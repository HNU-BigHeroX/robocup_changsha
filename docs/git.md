# Git 工作流程

每位参赛者使用一条编号分支保存参赛版本。小改动可以直接在编号分支上完成；需要单独试验的功能，可以另开功能分支，完成后合回本人编号分支。

无论使用哪种分支，都要先准备好分支，再创建或修改文件。首次开发的顺序是：确认编号 → 检查并准备分支 → 创建本人目录 → 开发。第一次克隆和复制模板的步骤见[获取仓库](how_to_fork.md)。

## 分支命名

| 分支                 | 用途                                     |
| -------------------- | ---------------------------------------- |
| `main`             | 官方主线，由组织方维护                   |
| `P017`             | 本人的参赛开发分支                       |
| `P017-obs-history` | 可选的功能分支，采用`Pxxx-功能名` 格式 |

示例中的 `P017` 都要换成自己的编号。所有个人分支都只能包含本人 `participant/P017/` 目录内的提交改动。

功能分支使用连字符，例如 `P017-obs-history`。不要命名为 `P017/obs-history`：Git 中已经存在 `P017` 分支时，无法再创建以它为路径前缀的分支。

选择是否创建功能分支时，可以使用下面的原则：

| 情况 | 建议 |
| --- | --- |
| 本人 `LOG.md`、`REPORT.md` 修正或小范围错误修复 | 直接在本人编号分支完成 |
| 需要多次训练或可能失败的实验 | 从本人编号分支创建功能分支 |
| 两个互不依赖的方案需要比较 | 分别创建功能分支，避免混在同一提交中 |
| 官方公共文件疑似有问题 | 不创建个人修复提交，记录复现并联系组织方 |

## 开始一次修改

先查看工作区和当前分支：

```sh
git status --short
git branch --show-current
```

如果有未提交的改动，先确认归属并妥善保存。不要为了切换分支而丢弃现有工作。

在编号分支上开发时：

```sh
git switch P017
```

需要功能分支时，从本人编号分支创建：

```sh
git switch P017
git switch -c P017-obs-history
```

如果功能分支已经存在，直接 `git switch P017-obs-history`。确认当前分支后再开始该功能的修改，不要先在 `main` 上开发，再补建分支。

开始修改前建议再检查一次分支与改动范围：

```sh
git branch --show-current
git status --short
git diff --name-only
```

分支名称、目录编号或现有改动归属不明确时，先停下来确认。尤其不要用 `git add .`、强制切换或清理命令掩盖范围问题。

## 提交和合并

只暂存本人的文件，再检查提交内容：

```sh
git add participant/P017/
git diff --cached
git commit -m "feat(P017): 增加目标速度的历史估计窗口"
```

提交前可以增加两项机械检查：

```sh
git diff --cached --check
git diff --cached --name-only
```

`git diff --cached --check` 用于发现已暂存文本中的多余空白和冲突标记，文件列表用于确认暂存区只包含本次任务。模型等二进制文件无法通过普通 diff 审阅时，应另外核对路径、大小和 SHA-256。

消息格式见[提交消息](cz.md)。功能完成并验证后，合回编号分支：

```sh
git switch P017
git merge --no-ff P017-obs-history -m "chore(P017): 合并目标历史估计功能"
git push -u origin P017
```

功能分支也可以推送到比赛仓库留存过程，但最终提交 PR 的来源分支必须是本人编号分支。

## 同步官方更新

先保存本人改动，确认工作区干净，再获取并合并官方主线：

```sh
git fetch origin
git switch P017
git merge origin/main
```

合并可以保留已经推送的开发历史，不需要强制推送。如果出现冲突，先查看涉及哪些文件。不要自行修改官方文件来消除冲突；涉及官方文件或他人目录时，联系组织方确认处理方式。

只在本人目录内发生的冲突，也应先比较两边内容再解决。解决后重新运行预检与相关实验，因为“Git 已合并”不等于策略行为没有变化。不要使用强制推送替代正常的冲突处理。

## 可选的版本标签

想标记一个可以复现的版本时，可以在编号分支上创建标签：

```sh
git switch P017
git tag P017/v1.0
git push origin P017/v1.0
```

标签格式是 `Pxxx/v<主版本>.<次版本>`。标签和分支使用不同的引用空间，因此这里的斜杠不会与编号分支冲突。已发布的标签不要移动到其他提交。

## 提交前检查

```sh
git fetch origin
git diff --name-only origin/main...P017
git status --short
```

第一条 diff 列出的提交文件应全部位于 `participant/P017/`。另看一次工作区状态，避免遗漏未提交的模型、代码或报告，也避免把缓存和测试输出加进去。

建议把最终检查分为三层：

1. **范围**：差异只在本人目录，没有模板、官方配置或其他参赛者文件。
2. **完整性**：入口、清单、模型、推理依赖、实验记录和许可证材料齐全。
3. **可复现性**：当前提交能通过预检和公开测试，结果能够对应到明确的代码与模型摘要。

如果 `git status --short` 仍有未提交内容，先确认这些内容是否属于最终版本。不要仅为了得到“干净工作区”而删除无法辨认的文件。

最终 PR 的标题为 `[P017] Final Submission`，从 `P017` 提交到 `main`，由组织方审核。时间窗口和版本冻结规则见[参与指南](../CONTRIBUTING.md)。
